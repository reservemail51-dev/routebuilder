# 実装計画（案）

> `docs/SPEC.md` を読んだうえでの実装計画です。**承認をいただくまで実装には着手しません。**
> 料金・規約・API 仕様は変わることがあるため、「要確認」と書いた項目は採用前に一次情報で確かめて ADR（設計判断の記録。`docs/adr/` に1判断1ファイルで残すメモ）に書きます。

---

## 1. 全体方針

- **最初にフロント単体で「引ける・見える・出せる」を作る。** ルート作成体験（Phase 1）が勝負所なので、ログインやDBより先に、地図・経由点編集・標高・出力を磨きます。
- **ロジックはすべて純粋関数のパッケージに分離**（`packages/geo`）。距離・リサンプリング・標高・勾配・登坂検出・トンネル補正・GPX/TCX/FIT 変換をここに置き、Vitest で厚くテストします。UI（React）はこれを呼ぶだけにします。
- **ルーティングはアダプタ層で抽象化**（`RoutingProvider`）。開発中は openrouteservice（ORS）、本番は自前 BRouter。フロントは Worker（ルーティングプロキシ）だけを見ます。
- **小さい PR を積む。** 1タスク＝1ブランチ＝1PR。各 PR に「何を変えたか／スマホでの確認方法／スクリーンショット」を日本語で書きます（スクリーンショットはクラウドセッション内の Playwright で撮影）。

## 2. リポジトリ構成（予定）

```
routebuilder/
├─ apps/
│  ├─ web/            … Vite + React + TS（Cloudflare Pages で配信）
│  └─ api/            … Cloudflare Workers + Hono（ルーティングプロキシ、後に認証・保存）
├─ packages/
│  ├─ geo/            … 地理計算の純粋関数（UI に依存しない）
│  ├─ formats/        … GPX / TCX / FIT の読み書き
│  └─ shared/         … 型定義（Route, Segment, Waypoint など）と設定値
├─ infra/
│  ├─ brouter/        … Dockerfile、自作プロファイル、セグメント取得スクリプト、VPS 手順書
│  ├─ tiles/          … PMTiles 切り出しスクリプト
│  └─ poi/            … OSM から POI を抽出するスクリプト（osmium）
├─ e2e/               … Playwright（PC 幅・スマホ幅）
├─ docs/  SPEC.md / PLAN.md / COSTS.md / adr/ / guides/（端末別の取り込み手順）
└─ CLAUDE.md          … 作業ルール（言語・コマンド・テスト・デプロイ）
```

パッケージ管理は **pnpm のワークスペース**（1つのリポジトリで複数パッケージを管理する仕組み）を使います。

## 3. データモデルの中心（区間単位ルーティング）

```ts
type Route = {
  waypoints: Waypoint[];          // 経由点（id, 緯度経度, 名前）
  segments: Segment[];            // waypoints[i] → waypoints[i+1] の区間
  defaultProfile: ProfileId;      // 'road' | 'road-lowtraffic' | 'no-steep' | 'hillclimb'
};
type Segment = {
  id: string;
  mode: 'snap' | 'straight';      // 道路スナップ／直線
  profile?: ProfileId;            // 区間だけ別プロファイルにする場合
  geometry?: LngLat[];            // ルーティング結果（無ければ仮の直線）
  tags?: WayTagRun[];             // tunnel/bridge/surface/highway などの区間内の連続タグ
  status: 'pending' | 'ok' | 'error';
};
```

- 経由点を1つ動かす → その前後2区間だけ再計算。
- 標高・統計は **区間ごとに計算してキャッシュし、合計だけ毎回出す**（300km・100点でも軽く）。
- Undo/Redo は「操作コマンドの履歴」で持つ（Zustand のストア＋コマンドパターン）。
- URL 共有は経由点をエンコード済みポリライン（緯度経度を短い文字列に圧縮する方式）＋区間モード＋プロファイルで表現。

### Phase 2：実走で役立つ情報

POI 抽出パイプライン（Geofabrik → osmium → PMTiles/GeoJSON、ビルド時のみ。本番で Overpass は使わない）→ POI レイヤーとルート沿い一覧・「次の補給まで◯km」→ 独自POI（サイクルオアシス等、管理画面）→ キューシート自動生成と編集（FIT/TCX のコースポイントへ反映、CSV・印刷）→ 所要時間の物理モデル（FTP・体重・機材）と通過予想時刻 → 風（Open-Meteo、条件確認後）→ 過去GPXの重ね表示（ブラウザ内処理）→ GPX/TCX/FIT 読み込みと編集可能ルートへの変換。

※ 独自POIの「管理画面」はログインが必要なため、Phase 2 の途中で**認証（Phase 3 の一部）を前倒し**します。

### Phase 3：一般公開サービス

認証（Google＋メールのマジックリンク。第一候補 Better Auth＋D1、ADR で確定）→ ルート保存・複製・フォルダ・公開範囲 → プライバシーゾーン（初期値で有効）→ 公開ルート検索 → 地域コース集（コースID・激坂レベル・補給情報、管理画面）→ OGP 画像生成 → 通報と非表示。

### Phase 4：設計だけ邪魔しない

PWA・オフライン、多言語化、Strava 連携、Garmin 直接送信。データモデルと URL 設計でこれらを塞がないようにだけ注意します。

## 5. 主要な技術判断（ADR にする予定のもの）

| 判断 | 第一候補 | 理由・メモ |
|---|---|---|
| 標高グラフ | Canvas 自前描画 | 勾配色分け・範囲選択・登坂ハイライト・地図同期を細かく制御でき、依存も増えない。点数が多いときは間引き（LTTB）で描画 |
| 住所・地名検索 | **国土地理院 住所検索API**＋自前の地名・駅名・峠名インデックス（OSM から抽出） | 日本語・無料・出典表示で利用可（要確認）。Nominatim 公開インスタンスは本番の自動補完に使えない |
| ルーティング（開発） | ORS `cycling-road` | 無料キーあり（日次上限あり・要確認）。返却情報に路面・道路種別・トンネル系フラグはあるが**橋のタグは取れない**見込み → 標高補正は急変検出フォールバックで補う |
| ルーティング（本番） | BRouter（自作プロファイル） | 道路タグを経路と一緒に返せるので、トンネル・橋補正と内訳バーが正確になる。BRouter 本体と同梱プロファイルは MIT ライセンス（要確認）なので、それを土台に自作 |
| FIT 出力 | Garmin 公式 FIT SDK（JS 版） | エンコード対応とライセンス（FIT Protocol License）の再配布条件を検証してから採用 |
| 認証 | Better Auth＋D1 | Workers で動き、Google と マジックリンクの両方に対応。D1 との接続方法を検証してから確定 |
| デプロイ | Pages の Git 連携 | GitHub 側に Cloudflare のトークンを置かずに済み、初心者でも設定が簡単 |
| ゴールデンルート試験 | GitHub Actions 上で BRouter を Docker 起動して実行＋記録済み応答での高速テスト | クラウドセッションでは BRouter を常駐できないが、CI なら毎回起動できる |

## 6. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| ORS の無料枠・利用条件 | 開発中に上限、公開後に条件違反の恐れ | Worker でキャッシュ・レート制限。**公開前に BRouter へ切替**を必須とする |
| OSM データの不備（しまなみの橋、自転車禁止区間のタグ漏れ） | ゴールデンルートで自転車禁止区間を通る | プロファイルで二重に除外（`motorroad`・`highway=motorway/trunk`＋`bicycle=no` 等）。ゴールデンルート試験で検知し、必要なら OSM 側の修正も検討 |
| DEM の誤差（橋・トンネル・切土） | 獲得標高の水増し、最大斜度の異常値 | タグ補間＋急変検出、平滑化とヒステリシス、移動窓勾配。基準値は一緒に確認 |
| 国土地理院タイルへの負荷・CORS | 表示不可、利用制限 | 取得タイルのキャッシュ、必要なら Worker 経由で中継 |
| スマホの操作衝突（地図移動と経由点追加） | 誤操作で使われなくなる | 追加モードの明示切替、長押し・ドラッグの判定調整、実機確認 |
| FIT の互換性 | Edge 840 で読めない／ClimbPro が効かない | 実機確認チェックリスト。GPX/TCX を常に代替として提供 |
| iOS Safari の Web Share API でのファイル共有 | Garmin Connect に直接渡せない | 案内ページ（図解）で代替 |
| 一般公開での悪用 | 費用増・サービス停止 | レート制限、経由点・距離・ファイルサイズ上限、通報機能 |
| PMTiles・POI の容量 | R2 の無料枠超過 | まず地域切り出し。`docs/COSTS.md` で見える化 |

## 7. 費用の見込み（概算・要確認）

- Cloudflare（Pages / Workers / D1 / R2 / KV）：公開初期は**無料枠内**の見込み。Workers の有料プラン（月 5 ドル）が必要になる可能性あり。
- BRouter 用 VPS：メモリ 1〜2GB の国内 VPS で**月 1,000 円前後**が目安（比較表は `infra/brouter/` の手順書で提示）。
- 独自ドメイン：年 1,500〜3,000 円程度（任意）。
- 詳細は `docs/COSTS.md` にまとめます。

## 8. 私（開発者）にご確認いただきたいこと

1. **main ブランチの作成**：リポジトリが空のため、今回のブランチ（`claude/new-session-jh1nox`）が既定ブランチになってしまいます。最初のコミットから `main` を作り、以後は「作業ブランチ → PR → main」で進めてよいですか。
2. **収益化の予定**：広告・寄付・有料プランを入れる予定はありますか。ORS・Open-Meteo・国土地理院などの「商用利用」の判断が変わります。
3. **運営者の表記**：利用規約・プライバシーポリシーに載せる運営者名（個人名／ハンドルネーム／屋号）と問い合わせ先をどうしますか。
4. **独自ドメイン**：最初は無料の `*.pages.dev` で始め、公開時に独自ドメイン（年 1,500〜3,000 円程度）を取る、でよいですか。
5. **Cloudflare アカウント**：作成済みですか。Pages の Git 連携・R2 バケット作成・環境変数の設定は、手順書を用意したうえで、ご自身で操作していただく必要があります。
6. **ORS の API キー**：無料登録でキーを取得していただけますか（取得手順は案内します）。
7. **BRouter の VPS**：Phase 1 の終盤で月 1,000 円前後の VPS 契約が必要になる見込みです。この時期と金額感で問題ないですか。
8. **標高の基準値**：別子山方面・石鎚スカイライン・しまなみの橋のアプローチについて、どの地点からどの地点まで（例：○○交差点 → ○○峠）を基準区間にしますか。地点だけ決めていただければ、地理院地図で一緒に値を確認します。
9. **激坂レベルの基準**：5段階の初期値（例：平均斜度と最大斜度・距離の組み合わせ）は私が案を作って設定ファイルにし、実際の峠で調整する、でよいですか。
10. **PR の進め方**：PR のマージ（取り込み）はご自身がスマホの GitHub アプリで行う想定でよいですか。私に任せる範囲があれば教えてください。

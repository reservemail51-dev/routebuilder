# ロードバイク向けルートビルダー 仕様書（SPEC）

> 最初の依頼メッセージの全文。以後の判断基準とする。変更する場合は PR で差分を残すこと。

あなたはこのプロジェクトのリードエンジニア兼プロダクトデザイナーです。日本のロードバイク乗りが**毎週実際に使い続けられる**ルートビルダーを、一般公開のWebサービスとして作ります。最初に、このメッセージ全文をリポジトリの `docs/SPEC.md` に保存し、以後の判断基準にしてください。

## 0. 目的と勝ち筋

- 目的：ルートラボ（2020年終了）の後継が国内に存在しない空白を埋める、「日本語・無料・登録なしでも使える・GPX/FIT出力まで無料」のルートビルダー。
- 手本：操作感は Ride with GPS、設計とコードは gpx.studio（MIT）、ルーティングの中身は BRouter-Web、路面内訳表示は Komoot、日本語の指標表現は NAVITIME。
- 差別化（大手が持っていないもの）：
  1. 日本の道路事情に合わせたロードバイク用ルーティング（自動車専用道路・自転車通行禁止・階段・未舗装を確実に避ける）
  2. 国土地理院データによる正確な標高と、トンネル・橋の標高補正
  3. 日本の補給事情に合わせたPOI（コンビニ・自販機・トイレ・道の駅・サイクルオアシス）
  4. 新居浜・東予・石鎚・しまなみ・四国一周の地域コース集（コースID、激坂レベル付き）
- 「クリックで引く・道路スナップ・標高グラフ・GPX出力」は最低限の機能であり、ここで手を抜かないこと。速さと操作の気持ちよさで Ride with GPS の無料版を上回ることを目標にする。

## 1. 前提・制約

- 開発者（私）は GitHub 初心者で、Claude Code をスマホ／クラウドセッションで使う。**説明・コミットメッセージ・README・UI文言はすべて日本語**。専門用語は初出で一言説明する。
- クラウドセッションでは常駐サーバー（BRouter）を動かせない前提で進める。ルーティングはアダプタ層で抽象化し、開発中は外部API、本番は自前ホストに切り替えられるようにする。
- 一般公開サービスなので、ライセンス・利用規約・個人情報・コスト・悪用対策を最初から設計に入れる。
- 運用コスト目標：公開初期は月数千円以内。有料サービスや規約上グレーなものを採用する前に、必ず私に確認する。
- 私の主な利用環境：iPhone と PC。サイコンは Garmin Edge 840（コースポイントと ClimbPro を活用したい）。

## 3. アーキテクチャの要点

- **区間単位ルーティング**：ルートは「経由点の配列＋区間ごとの経路」で持つ。経由点を1つ動かしたら、前後2区間だけ再計算する。300kmのブルベ級ルートでも編集が重くならないこと。
- **区間ごとのモード**：各区間は「道路スナップ（プロファイル指定）」か「直線（手動）」を持てる。直線区間も DEM から標高を出す（NAVITIME の「直線区間は標高0」問題を起こさない）。
- **ルーティングプロキシ**：ブラウザ → Worker → BRouter/ORS。Worker で IP 単位のレート制限、(始点, 終点, プロファイル) をキーにしたキャッシュ、タイムアウト時のフォールバックを行う。
- **URL共有**：ログインなしでも、経由点（エンコード済みポリライン）＋プロファイル＋区間モードを URL に埋め込んで共有・復元できる（GraphHopper Maps 方式）。
- **編集状態はローカルに自動保存**（IndexedDB）。ブラウザを閉じても作業が消えない。
- 地理計算（距離、勾配、平滑化、登坂検出、キュー生成）はUIから切り離した純粋関数のモジュールにし、単体テストを厚くする。

## 4. ルーティングプロファイル（日本向けに調整）

BRouter のプロファイルを `fastbike` / `fastbike-lowtraffic` をベースに自作し、リポジトリで管理する。第三者の GPL/AGPL プロファイルはコピーしない。

1. **ロード標準**：舗装路のみ。速さ重視。
2. **ロード・交通量少なめ**：国道・幹線のペナルティを上げ、県道・農道・海沿いを優先。
3. **激坂回避**：勾配のペナルティを強める（初心者・ファミリー向け）。
4. **ヒルクライム**：登りを避けない（峠を通したいとき用）。

全プロファイル共通の必須ルール：
- `motorroad=yes`（自動車専用道路）、`highway=motorway/trunk の自転車禁止区間`、`bicycle=no`、`highway=steps`、未舗装（`surface=unpaved/gravel/dirt` 等）を通さない。
- しまなみ海道の橋は自転車歩行者道を通ること。
- トンネルは通行可だが、長いトンネルは軽いペナルティ（代替路があればそちらを選ぶ程度）。

## 5. 標高処理の仕様

- ルート上を一定間隔（例：20m）でリサンプリングし、DEM から標高を取得。取得したタイルはキャッシュする。
- **トンネル・橋の補正**：ルーティング結果の道路タグ（`tunnel=yes` / `bridge=yes`）区間は、入口と出口の標高を直線補間する。タグが取れない場合は、急激な標高変化を検出して補間するフォールバックを用意する。
- 獲得標高は平滑化＋ヒステリシス（しきい値は設定ファイルで調整可能）で計算し、GPSノイズや DEM の段差で水増ししない。
- 勾配は区間距離（例：100m移動窓）で計算し、「最大勾配」が数メートルの誤差で極端な値にならないようにする。
- 計算結果は、既知の峠（別子山方面、石鎚スカイライン、しまなみの橋のアプローチなど）で実際の値と大きくずれないことをテストで確認する。基準値は国土地理院の地図で私と一緒に確認して決める（推測で数値を作らない）。

## 6. 機能要件（フェーズ別。各フェーズの終わりに「公開URLで動く状態」にする）

### Phase 0：土台（半日〜1日）
- リポジトリ構成、`CLAUDE.md`（作業ルール）、`docs/adr/`、Cloudflare Pages への自動デプロイ、地図表示（PMTiles＋国土地理院レイヤー切替）、クレジット表示。
- 完了条件：スマホで地図が表示され、レイヤーを切り替えられる。

### Phase 1：最高のルート作成体験（MVP。ここに最も時間をかける）
- タップ／クリックで経由点を追加し、道路にスナップしたルートを引く。
- 経由点のドラッグ移動、ルート線をドラッグして経由点を挿入、経由点の削除。
- Undo / Redo（PC はショートカット、スマホは大きなボタン）。
- 区間ごとの「直線モード」切り替え。プロファイルの切り替え（全体／選択区間のみ）。
- 便利操作：往復にする、逆走にする、スタートへ戻って周回を閉じる、周回ルートのスタート地点を変更、選択区間の削除・引き直し。
- 住所・地名検索（Nominatim の公開インスタンスは規約上の制限があるため、本番用の方式を ADR で決める）。
- 統計パネル：総距離、獲得標高、下降、最高標高、平均斜度、最大斜度、予想所要時間、トンネル数と総延長（ライト必須の目安）。
- 標高グラフ：勾配で色分け。グラフ上のホバー／タップで地図上の位置を同期表示。グラフの範囲をドラッグで選ぶと、その区間の距離・獲得標高・平均斜度を表示。
- **登坂の自動検出**：一定以上の登りを自動で切り出し、長さ・獲得標高・平均／最大勾配・「激坂レベル（5段階、基準は設定化）」を一覧表示。地図とグラフでハイライト（Garmin の ClimbPro と同じ感覚で事前確認できること）。
- 路面・道路種別の内訳バー（Komoot 方式：舗装／未舗装、国道／県道／市町村道／自転車道など）。
- 出力：GPX（トラック＋標高＋ウェイポイント）、TCX（コースポイント付き）。FIT コースは Garmin 公式 FIT SDK（JavaScript版）でエンコードできるか検証し、可能なら Phase 1 に含める。
- スマホでは Web Share API でファイルを各社アプリ（Garmin Connect など）に渡せるか実機で検証し、ダメなら「ダウンロード→各社アプリで取り込む」手順を図解した案内ページを用意する（Garmin Edge 840 / Wahoo / Karoo / Bryton / iGPSPORT）。
- URL 共有と IndexedDB への自動保存。
- 完了条件：私がスマホだけで「新居浜駅 → 別子山 → 新居浜駅」の周回を5分以内に作り、FIT か GPX を Edge 840 に入れて走れること。

### Phase 2：実走で役立つ情報
- POI レイヤー：コンビニ、自販機、トイレ、水場、道の駅、駐輪場、自転車店。ルートから指定距離以内のものを一覧化し、「次の補給まで◯km」をキューシートに表示。
- サイクルオアシス等、OSM にない地域情報は管理画面から手で登録できる独自 POI として持つ。
- キューシート自動生成（曲がる交差点、補給、登坂開始）。編集可能で、FIT/TCX のコースポイントに反映。CSV・印刷用表示も出力。
- 予想所要時間を2方式で：①平地巡航速度＋登坂速度（VAM）の簡易方式、②FTP・体重・機材重量から計算する物理モデル。区間ごとの通過予想時刻を出す。
- 風：出発日時を入れると、区間ごとの向かい風／追い風を表示（Open-Meteo 等。商用利用条件を確認してから採用）。
- 自分の過去の走行 GPX を読み込んで、地図上に重ねて表示（ブラウザ内で処理し、サーバーに送らない）。
- GPX / TCX / FIT の読み込みと、読み込んだトラックを経由点付きの編集可能ルートに変換。

### Phase 3：一般公開サービスとしての機能
- アカウント、ルートの保存・複製・フォルダ分け、公開範囲（非公開／限定公開URL／公開）。
- **プライバシーゾーン**：自宅周辺など指定した円の中は、公開ルートで始点・終点をぼかす（Strava 方式）。初期値で有効にする。
- 公開ルートの検索：エリア（地図範囲）、距離、獲得標高、周回／片道、激坂レベルで絞り込み。
- 地域コース集：コースID（例：`EH-NI-01`）、難易度、激坂レベル、見どころ、補給情報、GPX／FIT のダウンロード。私が管理画面から登録できるようにする。
- OGP画像（ルート形状と距離・獲得標高）を生成し、LINE・X で共有したときに見栄えがするようにする。
- 不適切なルート・スパムの通報と非表示機能。

### Phase 4：後回しでよいもの（設計だけ邪魔しない）
- PWA・オフライン地図、多言語化、Strava 連携（2026年の API 有料化と表示制限を踏まえて要否を再検討）、Garmin への直接送信（Developer Program の新規受付停止中のため現時点では実装しない）。

## 7. UI / UX 要件

- **スマホ最優先**。地図を最大化し、統計と標高グラフは下からのボトムシート（3段階の高さ）。タップ領域は44px以上。片手で操作できる配置。
- 誤タップ対策：スマホでは「経由点追加モード」のオン／オフを明示的に切り替える。地図の移動・拡大と経由点追加が衝突しないこと。
- PC ではサイドパネル＋ショートカット（Undo/Redo、削除、モード切替）。
- 言葉は国内サイクリストに馴染んだ表現を使う：「獲得標高」「平均斜度」「最大斜度」「激坂」「補給」「周回」「往復」。
- 操作のフィードバックは即時に：経由点追加 → 仮の直線を即表示 → ルーティング結果で置き換え。エラー時は直線のまま残して理由を表示。
- 初回だけ30秒で分かる操作ガイド。登録なしで全部の作成・出力機能が使えること（保存と公開だけログインが必要）。
- アクセシビリティ：色だけに頼らない勾配表示（凡例と数値）、ダークモード対応。

## 8. 公開サービスとしての必須事項

- クレジット：「© OpenStreetMap contributors」「出典：国土地理院」、Protomaps、ルーティングエンジンを地図上の見える位置に常時表示。
- 利用規約、プライバシーポリシー、免責（ルートは参考であり、交通規則・通行止め・自転車通行可否は現地で確認すること）のページ。
- 外部サービス（ORS、Nominatim、Open-Meteo など）は、それぞれの利用規約と商用利用条件を ADR に記録してから使う。OSM 公式タイルは本番で使わない。Strava のヒートマップタイルは使わない。
- 悪用対策：ルーティング API のレート制限、1ルートあたりの経由点上限・距離上限、アップロードファイルのサイズ制限と検証。
- 秘密情報（APIキー等）はコードに書かず、Cloudflare の環境変数で管理し、`.dev.vars.example` で必要な値を示す。
- 費用の見える化：主要な従量課金の項目と、無料枠を超えたときの概算を `docs/COSTS.md` にまとめる。

## 9. 品質基準

- **ゴールデンルート（受け入れテスト）**：以下をルーティングして、自動車専用道路・自転車禁止区間・階段・未舗装を通らないことを自動テストで確認する。
  - 新居浜駅 → 別子山 → 新居浜駅（周回）
  - 尾道 → 今治（しまなみ海道。橋は自転車歩行者道を通る）
  - 西条 → 石鎚山方面の登り
  - 新居浜 → 松山（国道11号周辺。自転車が通れない区間を避ける）
- 単体テスト：距離計算、リサンプリング、獲得標高の平滑化、勾配、登坂検出、トンネル補正、GPX/TCX/FIT の書き出し→読み込みの往復一致。
- E2E：スマホ幅と PC 幅で、ルート作成 → 編集 → Undo → 出力 の一連の操作。
- 性能目標：キャッシュ済み区間の再描画は体感即時、未キャッシュでも区間あたり1秒以内を目標。300km・経由点100点のルートでドラッグと標高グラフ操作がカクつかない。スマホでの初回表示を軽く保つ（地図とグラフのライブラリ以外は遅延読み込み）。
- 本番に出す出力ファイルは、Garmin Connect への取り込みと Edge 840 での表示を私が実機確認する項目としてチェックリスト化する。

## 10. 作業の進め方

1. 最初に、このSPECを読んだうえでの**実装計画（フェーズごとのタスク、リスク、私に確認が必要な事項）**を出し、私の承認を待つ。
2. 不明点は推測で埋めず、まとめて質問する。ただし技術的に一般的な選択は自分で決めて ADR に残す。
3. 1タスク＝1ブランチ＝1プルリクエスト。PR の説明に「何を変えたか」「スマホでの確認方法」「スクリーンショット」を日本語で書く。
4. 各フェーズの終わりに、公開URLで私が確認する**チェックリスト**を渡す。
5. BRouter の本番環境は、クラウドセッションでは動かせないため、`infra/brouter/` に Dockerfile、プロファイル、セグメント取得スクリプト、VPS での立ち上げ手順書（初心者向けにコマンドを1行ずつ説明）を用意する。VPS の候補と月額の目安も比較して提示する。
6. `CLAUDE.md` に、このプロジェクトの決まりごと（言語、コマンド、テストの回し方、デプロイ方法）を書き、セッションをまたいでも同じ品質で続けられるようにする。

まずは手順1の実装計画から始めてください。
